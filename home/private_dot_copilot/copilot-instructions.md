# Copilot Instructions (User-Level)

## ツール操作の制約

- Python は `python` / `pip` を直接実行しない。スクリプトと REPL は `uv run`、依存追加は `uv add` または `uv pip install` を使う
- Windows でシェルからファイルを開く場合は `Start-Process edit <path>`、Markdown は `Show-Markdown -Path <path> -UseBrowser` を使う
- Windows の PowerShell から `.sh` を実行する場合は `$env:MSYS_NO_PATHCONV = "1"` を設定し、`& "C:\Program Files\Git\bin\bash.exe" <script>` を使う
- macOS / Linux のコマンド存在確認は `command -v` を使い、`which` は使わない

## 言語

- 日本語で応答する（文脈上明らかに英語が必要な場合を除く）
- コードコメント、ドキュメント、コミット説明、PR 本文は README の言語に従う
- コミットメッセージの Conventional Commits プレフィックスとブランチ名は英語
- 日本語の技術文書を Markdown ファイルとして作成、推敲、レビューするときは `japanese-technical-writing` スキルを使う。通常のチャット応答は対象外

### 再考する表現

以下の語を使うときは、対象、操作、役割、条件を具体的に書けないか再考する。別の曖昧な語へ機械的に置き換えず、文意に応じて文全体を書き直す。語ごとの判断基準は次に従う。

| 語 | 判断基準 |
|---|---|
| 寄せる | 物理的な意味以外では避ける。合わせる、統一する、準拠するなど、具体的な動作を書く |
| 正本 | 使用を避ける。定義元、参照先、管理元など、指している役割を書く |
| 経路 | 手段、手順、条件の総称として使わず、何を使い、どの条件で何をするかを書く。通信や探索など、通過点や順序そのものを表す場合は使ってよい |
| 座標 | 対象の所在や識別情報、集計単位を曖昧に表す語として使わず、ファイルパス、行番号、リソース宣言の数など、何を指し、何を数えているかを具体的に書く。数学、地理、画面上の位置など、座標そのものを表す場合は使ってよい |
| 境界 | 対象範囲、責務、管理主体の区切りを曖昧に表す語として使わず、何と何を分けるのか、どちらが何を担うのかを具体的に書く。システム境界、信頼境界、ネットワーク境界など、区切り自体が技術的概念である場合は使ってよい |
| 契約 | 仕様、保証条件、テスト対象、互換性要件などをまとめて曖昧に表す用途では避ける。誰が何を満たすのか、どの条件を実装やテストで確認するのかを書く。API contract や contract test など、定義された技術用語を指す場合は使ってよい |
| ベストプラクティス | 生成文では使用を避け、何がどの条件で推奨されるのかを具体的に書く。「推奨事項」「定番の方法」などへ機械的に置き換えない。検索クエリなど、固有の用語を指定する場合は使ってよい |

## 通常応答の文体

- 段落を基本とし、見出し、箇条書き、表は文章だけより分かりやすくなる場合に使う
- 大げさな形容、不要な比喩、曖昧な流行語を避け、具体的で平易な言葉を使う。技術的な精度に必要な専門用語は残す

## 記述の置き場所

- **指示とエージェント**: 可能な限りシンプルにし、モデルが持つと期待される一般知識は省く。固有の行動規範は指示に、タスク固有の手順はエージェントやスキルに記載し、memory に蓄積しない
- **コードコメント**: コードから読み取れない意図、制約の出所、回避策の要点を書く。判断の経緯や変更履歴は置かない
- **判断の記録（ADR 等）**: 設計判断と根拠を残す。実装の詳細、検証ログ、操作手順は置かない
- **手順と構造の文書**: 現在の構造と操作方法を書く。判断の背景は判断の記録を参照する

回避策を入れるときは、撤去条件と対象範囲を一箇所へ集約し、コード側には要点だけを残す。集約先はリポジトリ側の定めに従う。

## 図解

- Markdown の図は `mermaid` タグを使い、`c4` タグは使わない
- C4 は Mermaid C4 構文を使い、一つの図で一つの抽象レベルを扱う。未対応の UI では `flowchart` で同じ抽象レベルを表す
- 主要な要素と関係は図だけでなく本文でも説明する

## エージェント行動規範

- **作業範囲**: 調査のみの依頼ではリポジトリを編集しない
- **コミット / push**: それぞれ明示的な指示がある場合だけ実行する。編集の許可を commit や push の許可とみなさない。編集後は `git diff --stat` と要約を提示する
- **テストコード**: 将来の回帰テストに必要なものだけを追加する。一度きりの確認に使うテストコードは一時ディレクトリに作成し、コミットしない

## 調査とスキル

- 短い連続した調査は直接行う。独立した大きな調査や専門判断は委譲し、要約、根拠、未確認事項を受け取る。ファイル数や行数だけで委譲を決めない
- 長い資料は必要箇所を絞り、精読を委譲した範囲は重複調査しない
- 必要なスキルや委譲機能が利用できなければ、その制約と進められる範囲を明示する
